# SafeVege Manuals Design

วันที่: 17 ตุลาคม 2026
สถานะ: อนุมัติให้ดำเนินการ

## เป้าหมาย

สร้างคู่มือภาษาไทยแบบ PDF จำนวน 2 ฉบับจากสถานะจริงของโปรเจกต์ SafeVege:

1. คู่มือผู้ใช้ทั่วไป สำหรับผู้เยี่ยมชม ผู้บริโภค ผู้ประกอบการร้านค้า Inspector Admin และ Super Admin ที่ไม่จำเป็นต้องรู้การเขียนโปรแกรม
2. คู่มือนักพัฒนา สำหรับผู้ดูแลโค้ด ระบบ API ฐานข้อมูล การตั้งค่าเครื่อง การทดสอบ การ deploy และการพัฒนาต่อ

ชื่อไฟล์และคำสั่งในโค้ดยังคงใช้ภาษาอังกฤษเพื่อให้คัดลอกไปใช้งานได้จริง แต่คำอธิบายทั้งหมดเป็นภาษาไทย

## แนวทางที่เลือก

จัดทำเป็น PDF แยก 2 ไฟล์ เพื่อให้แจกตามกลุ่มผู้อ่านได้ง่ายและไม่ทำให้คู่มือผู้ใช้มีรายละเอียดเชิงเทคนิคเกินจำเป็น โดยใช้รูปแบบเอกสารเดียวกัน ได้แก่ หน้าปก สารบัญ เลขหน้า หัวข้อย่อย ตาราง และแผนภาพแบบอ่านง่าย

เนื้อหาจะอ้างอิงจากไฟล์จริงใน repository เช่น `fn/safevege/README.md`, `bn/README.md`, `bn/schema.sql`, โค้ดหน้าจอ Flutter, repository/API client, route ของ PHP และ test files หากเนื้อหาใดไม่มีหลักฐานในโปรเจกต์จะระบุเป็นคำแนะนำหรือข้อจำกัด ไม่เขียนให้เป็นความสามารถที่ยืนยันแล้ว

## ขอบเขตคู่มือผู้ใช้

- ภาพรวม SafeVege และการเลือกบทบาท
- การค้นหาร้านจาก feed และแผนที่ OpenStreetMap
- การดูรายละเอียดร้าน ใบรับรอง และการนำทาง
- การสมัคร/เข้าสู่ระบบของร้านค้า
- การแก้ไขข้อมูลร้านและการเลือกพิกัด
- การสร้างคำขอตรวจผักหลายรายการและติดตามสถานะ
- การจัดการนัดหมาย ผลตรวจ และเอกสารใบรับรองสำหรับผู้ดูแล
- การจัดการบัญชี บทบาท การตั้งค่า และ audit สำหรับ Super Admin
- ตารางความหมายของสถานะและวิธีแก้ปัญหาทั่วไป
- คำเตือนเรื่องข้อมูลสาธารณะ ใบรับรอง และการเก็บรหัสผ่าน

## ขอบเขตคู่มือนักพัฒนา

- ภาพรวมระบบ 3 ส่วน: Flutter frontend, PHP REST API และ MySQL
- โครงสร้าง `fn/safevege` และ `bn` พร้อมหน้าที่ของโฟลเดอร์สำคัญ
- data flow จาก `main.dart` ผ่าน `AppState`, repository, `ApiClient` ไปยัง API
- บทบาท `shop`, `admin`, `super_admin`, token และการตรวจสิทธิ์
- API ตามกลุ่ม public, auth, shop และ admin
- ER/data model ของผู้ใช้ ร้าน คำขอตรวจ นัดหมาย ผลตรวจ ใบรับรอง audit และ settings
- ขั้นตอนตั้งค่า local API, MySQL, CORS, Flutter และ Android Emulator
- การสร้าง admin แรก การโหลด demo data และข้อควรระวัง migration
- แนวทางเพิ่มฟีเจอร์และแก้ไขข้อมูลโดยรักษา API contract
- การทดสอบ analyzer, unit/widget/API/integration และ release build
- ความปลอดภัยของ `.env`, password hash, bearer token และไฟล์ใบรับรอง
- ข้อจำกัดปัจจุบัน จุดที่เป็น draft และรายการพัฒนาต่อ

## การตรวจสอบเนื้อหา

- ใช้ข้อมูลจาก branch และไฟล์ที่ตรวจพบในวันที่จัดทำเอกสาร
- ระบุ path ของไฟล์อ้างอิงในคู่มือนักพัฒนา
- ตรวจคำสั่งในคู่มือกับ README และไฟล์ config ก่อนใส่ใน PDF
- ตรวจว่าไม่มี password, token, `.env` จริง หรือข้อมูล production ถูกฝังในเอกสาร
- สร้าง PDF ด้วยฟอนต์ภาษาไทยที่ฝังในไฟล์
- เรนเดอร์ทุกหน้าเป็นภาพเพื่อตรวจการตัดขอบ ตารางซ้อน ตัวอักษรหาย และเลขหน้า
- ตรวจข้อความด้วยการแยกข้อความจาก PDF และตรวจจำนวนหน้า/metadata

## เกณฑ์ส่งมอบ

- มี PDF 2 ไฟล์อยู่ใต้ `output/pdf/`
- เปิดอ่านได้ทั้งสองไฟล์และมีสารบัญ/เลขหน้า/หัวข้อครบ
- ภาษาไทยแสดงผลได้โดยไม่เป็นสี่เหลี่ยมหรืออักขระหาย
- คู่มือผู้ใช้ไม่พึ่งพาความรู้ด้านโค้ด
- คู่มือนักพัฒนาระบุคำสั่ง path และข้อจำกัดที่ตรงกับโปรเจกต์ปัจจุบัน
- ผลการตรวจสอบและข้อจำกัดที่ยังทำไม่ได้จะถูกระบุอย่างตรงไปตรงมา
